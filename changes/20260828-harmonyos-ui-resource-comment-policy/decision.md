# HarmonyOS 页面、资源与中文注释策略决策

- Status: approved
- Date: 2026-08-28
- Decision owners: `platform-harmony`（用户明确确认按建议约定实施）

## 背景

Domain 已有 MVVM、页面/Dialog/组件分类和 ArkUI V2 约束，但缺少 UI 资源化、HMRouter 结构和中文
逻辑注释的闭环规则。新增 sample 为这些约定提供了项目级入口，但其初始状态本身尚未符合目标规范。

## 备选方案

1. 只修改 sample：易理解但无法形成持久、可评估的 Domain 行为。
2. 只修改 Skill：执行时可见，但规则权威、评估门槛和迁移影响不清楚。
3. 同时更新参考、规则、工作流、Skill、评估器、证据模板和版本：覆盖完整交付闭环。

## 决策

采用方案 3。资源化和职责注释作为 Domain 强制规则；中文语言要求以本次 Domain Owner 明确指令为
权威输入。HMRouter 是支持的项目路由框架之一，不提升为 HarmonyOS 平台标准。项目未使用 HMRouter
时仍须满足等价的集中路由、页面/Dialog 分类、资源和注释结果。由于新规则会令旧交付在新评估器下
失败，版本升级为 3.0.0，并提供迁移说明。

### 2026-08-28 评估语义修订

Domain Owner 指出首轮评估把“版本不一致/API 警告”直接等同于“行为失败”的标准不成立。现修订为：

- core/plugin 版本差异和生成 API 级别警告默认作为 compatibility warning 与残余风险；
- warning 只限制它实际支持的兼容性声明，不自动使页面、Dialog、路由、资源或注释交付失败；
- 只有观察到构建/必需运行场景失败，或项目明确规定版本相等、禁止该 API 等硬门槛时才判 `fail`；
- 只有任务明确要求某项兼容性结论且必要目标证据不可用时，才对该结论判 `blocked`；
- 不得用成功构建抹去真实结构错误，也不得用 warning 虚构尚未观察到的功能失败。

首轮独立 `Fail` 报告作为历史证据保留，不删除、不改写；修订后的制品必须重新独立评估。

## 后果

- 新增或实质修改的 UI 需要额外资源和注释审查。
- 旧项目可以继续固定 2.x；迁移到 3.0.0 时必须处理受影响 UI，而不是一次性翻译或重写全部遗留代码。
- 构建成功不再能掩盖目录、硬编码资源或缺少有意义中文注释的问题。

## 重新审视条件

- HarmonyOS 资源机制或 HMRouter 声明方式发生版本性变化。
- Owner 采用新的组织注释语言策略。
- 自动检查出现不可接受的误报，且可以由更精确的结构化检查替代。
